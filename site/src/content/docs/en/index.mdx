## A job that silently stops looks exactly like a job with nothing to do

A nightly backup, an export, a certificate renewal, a billing run, a worker: when one of these **scheduled jobs** stops running, no error is raised and nobody is told. It is sometimes noticed weeks later, by whoever needed yesterday's data.

Ordinary **job monitoring** watches for what went wrong. SilenceWatch watches for **what did not happen**: it is a *dead man's switch*. You declare how often a task should run and how late it may be. If it does not check in on time, the alert goes out.

## Cron job monitoring in three steps

<Steps>

1. **Declare the job.** Create a check with its frequency (every 15 minutes) or its cron expression (`0 2 * * *`), its time zone and the lateness you tolerate.

2. **Call the ping URL when the job finishes.** A plain HTTP request; `curl` is enough:

   ```bash title="crontab"
   0 2 * * *  /usr/local/bin/backup.sh && curl -fsS -m 10 --retry 3 https://app.silencewatch.com/p/<ping-key>
   ```

3. **Get alerted if it does not arrive.** The check goes late, then down; an incident opens and every enabled channel is notified: email, webhook, Slack, Microsoft Teams or Discord. The next ping resolves the incident and sends a recovery alert.

</Steps>

The details of the endpoints (`/start`, `/fail`, exit code, duration) are in the [ping API documentation](/en/docs/ping-api/). Copy-paste examples for crontab, systemd, Docker, Kubernetes and GitHub Actions are in the [cron monitoring examples](/en/docs/cron-examples/).

## Which jobs?

Anything that must run at regular intervals and whose absence matters: [cron backup monitoring](/en/guides/backup-monitoring/), data imports and exports, billing runs, purges, certificate renewals, workers and task queues. If the job can call a URL, it can be monitored. See also general [job monitoring](/en/job-monitoring/) and [what a dead man's switch is](/en/dead-mans-switch/).

## Spring Boot: nothing to declare by hand

```xml title="pom.xml"
<dependency>
  <groupId>com.silencewatch</groupId>
  <artifactId>silencewatch-spring-boot-starter</artifactId>
  <version>0.1.0</version>
</dependency>
```

```yaml title="application.yml"
silencewatch:
  api-key: ${SILENCEWATCH_API_KEY}
```

At startup the starter reads the tasks **Spring itself scheduled** (with the cron expressions as they actually resolved) and the Quartz jobs, declares them to SilenceWatch, then sends a heartbeat around every run, with its duration and any exception. It never fails and never blocks your job. [All about Spring Boot monitoring](/en/spring-boot/).

## Hosted or self-hosted, never crippled

SilenceWatch is released under the **Apache 2.0** licence. Use it as the hosted service at [app.silencewatch.com](https://app.silencewatch.com), or [self-host it](/en/self-hosted/): one container and one PostgreSQL database, nothing else. There is no "enterprise edition" and no reserved feature: the hosted offer sells not running a server, not features.
