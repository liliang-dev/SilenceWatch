<p class="splash-lede">In a Python application, scheduled tasks multiply and nobody keeps the list up to date. The <strong>SilenceWatch library</strong> keeps it for you: it reads your Celery beat schedule or your APScheduler jobs, declares them with their real schedule, and reports every run.</p>

## One package, one key

```bash
pip install "silencewatch[celery]"       # or "silencewatch[apscheduler]"
export SILENCEWATCH_API_KEY=sw_...
```

```python title="Celery"
from silencewatch.integrations.celery import instrument

instrument(app)
```

```python title="APScheduler"
from silencewatch.integrations.apscheduler import instrument

instrument(scheduler)
```

Restart the application. Every scheduled task appears in SilenceWatch with its real schedule, and sends a heartbeat around every run, with its duration and its failures. No check to create by hand, no ping URL to copy, nothing to keep in sync when the code changes.

## What sets it apart

- **It reads the real schedules.** A `crontab(hour=2, minute=0)` is declared as `0 2 * * *`, in the time zone of your Celery app; an APScheduler `CronTrigger` or `IntervalTrigger` is read the same way.
- **It gives each job a stable identity** (`celery:shop.tasks.backup`, or the job id for APScheduler): history survives restarts, redeployments and renames.
- **It never deletes anything.** A job that disappears from the code is flagged *orphaned*; the history is kept until you decide to delete it.
- **It tells environments apart**: the same application declared in staging and in production yields two separate checks.
- **It is built to take more schedulers.** Celery and APScheduler are two modules of one small package; the next one is another module, with the same declaration and the same rules.

## It cannot hurt you

A monitoring tool that disturbs production is worse than none. The library follows strict rules:

- it **never fails** your job: every error is swallowed and logged at `WARNING`, and your task runs once, its result and its exception passing through unchanged;
- it **never blocks** your job: sending goes through a bounded queue and a daemon thread, and survives the fork of Celery's workers;
- it **degrades silently**: with no key, no network or no server, the application runs exactly as without it;
- `SILENCEWATCH_ENABLED=false` **removes the whole mechanism**;
- it has **no dependency**: the standard library only.

All settings and limits are in the [library documentation](/docs/python/).

## If your job is not Celery or APScheduler

Nothing forces you to use the library: any job that can make an HTTP request can be monitored with the [ping API](/docs/ping-api/). See [cron job monitoring](/cron-monitoring/) and the [examples](/docs/cron-examples/).
