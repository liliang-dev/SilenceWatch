Partout, le principe est le même : **faire une requête HTTP sur l’URL de ping quand le job réussit** (et, mieux, sur `/start` au début et sur `/fail` en cas d’échec). Remplacez `<clé-de-ping>` par la clé de votre check. Les options `-fsS -m 10 --retry 3` sont expliquées dans l’[API de ping](/docs/ping-api/).

<Tabs syncKey="platform">
<TabItem label="crontab">

Le plus simple : le ping part uniquement si le script réussit (`&&`).

```bash title="crontab -e"
0 2 * * *  /usr/local/bin/backup.sh && curl -fsS -m 10 --retry 3 https://app.silencewatch.com/p/<clé-de-ping>
```

Pour mesurer la durée et signaler l’échec explicitement, passez par un petit script :

```bash title="/usr/local/bin/backup-monitored.sh"
#!/bin/sh
URL=https://app.silencewatch.com/p/<clé-de-ping>
curl -fsS -m 10 --retry 3 "$URL/start"
/usr/local/bin/backup.sh
curl -fsS -m 10 --retry 3 "$URL/$?"
```

</TabItem>
<TabItem label="systemd">

Dans le service lancé par le minuteur (*timer*) :

```ini title="/etc/systemd/system/backup.service"
[Service]
Type=oneshot
ExecStart=/bin/sh -c '/usr/local/bin/backup.sh && curl -fsS -m 10 --retry 3 https://app.silencewatch.com/p/<clé-de-ping>'
```

```ini title="/etc/systemd/system/backup.timer"
[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

</TabItem>
<TabItem label="Docker">

```bash
docker run --rm mon-image /app/job.sh \
  && curl -fsS -m 10 --retry 3 https://app.silencewatch.com/p/<clé-de-ping>
```

Dans un `docker-compose.yml`, vous pouvez enchaîner dans la commande du service : `command: sh -c "/app/job.sh && curl -fsS -m 10 --retry 3 $PING_URL"`, à condition que l’image contienne `curl`.

</TabItem>
<TabItem label="Kubernetes">

```yaml title="cronjob.yaml"
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: mon-image:latest
              command: ["/bin/sh", "-c"]
              args:
                - /app/backup.sh && curl -fsS -m 10 --retry 3 "$PING_URL"
              env:
                - name: PING_URL
                  valueFrom:
                    secretKeyRef:
                      name: silencewatch
                      key: ping-url
```

L’URL de ping est un secret : placez-la dans un `Secret`, pas dans le manifeste.

</TabItem>
<TabItem label="GitHub Actions">

```yaml title=".github/workflows/nightly.yml"
on:
  schedule:
    - cron: "0 2 * * *"
jobs:
  nightly:
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/nightly.sh
      - name: Ping SilenceWatch
        if: success()
        run: curl -fsS -m 10 --retry 3 "${{ secrets.SILENCEWATCH_PING_URL }}"
      - name: Signaler l’échec
        if: failure()
        run: curl -fsS -m 10 --retry 3 "${{ secrets.SILENCEWATCH_PING_URL }}/fail"
```

Les workflows planifiés de GitHub peuvent être retardés ou sautés ; c’est précisément le genre d’absence qu’un dead man’s switch détecte.

</TabItem>
<TabItem label="Python">

```python
import requests

URL = "https://app.silencewatch.com/p/<clé-de-ping>"

requests.get(f"{URL}/start", timeout=10)
try:
    run_job()
except Exception:
    requests.get(f"{URL}/fail", timeout=10)
    raise
else:
    requests.get(URL, timeout=10)
```

</TabItem>
<TabItem label="Node.js">

```js
const URL_PING = 'https://app.silencewatch.com/p/<clé-de-ping>';

await fetch(`${URL_PING}/start`, { signal: AbortSignal.timeout(10_000) });
try {
  await runJob();
  await fetch(URL_PING, { signal: AbortSignal.timeout(10_000) });
} catch (error) {
  await fetch(`${URL_PING}/fail`, { signal: AbortSignal.timeout(10_000) });
  throw error;
}
```

</TabItem>
<TabItem label="PowerShell">

```powershell title="Planificateur de tâches Windows"
$url = "https://app.silencewatch.com/p/<clé-de-ping>"
& "C:\Jobs\backup.ps1"
if ($?) { Invoke-RestMethod -Uri $url -TimeoutSec 10 }
else { Invoke-RestMethod -Uri "$url/fail" -TimeoutSec 10 }
```

</TabItem>
</Tabs>

<Aside type="caution" title="Un ping qui échoue ne doit pas faire échouer votre job">
Si SilenceWatch est injoignable, votre job ne doit pas en souffrir : `--retry 3 -m 10` borne l’attente, et dans un script vous pouvez ajouter `|| true` après le `curl` si l’échec du ping ne doit jamais changer le code de sortie.
</Aside>

## Pour Spring Boot

N’écrivez rien : le [starter Spring Boot](/docs/spring-boot/) découvre les `@Scheduled` et les jobs Quartz et envoie les pings à votre place.
